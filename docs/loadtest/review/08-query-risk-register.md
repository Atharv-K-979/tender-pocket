## A. Approval endpoint: p95 ~55 s at both 50K and 100K tenders

### A.1 End-to-end trace

Browser → Next.js `GET /api/approvals/counts` (`frontend/src/app/api/approvals/counts/route.ts:3-6`) or `GET /api/approvals/pending` (`…/approvals/pending/route.ts:3-6`) → `proxyToBackend` (`frontend/src/lib/backendProxy.ts:46`, no timeout) → Spring `AC:360` / `AC:498`. The `frontend/src/lib/approvalsSync.ts` reconcile is **never called** (VERIFIED).

**`GET /api/approvals/counts` (`AC:360-457`), in order:**
1. `AC:371` `reconcileStaleAndDuplicateApprovals()`, which is **not transactional** (Q04a):
   - `AC:143` all PENDING approvals (Q06; seq scan plus sort).
   - `AC:147` `findAllById(distinct tenderIds)` (Q07; IN-list, full entities).
   - Loop over (tender, stage) groups, `AC:155-233`: `delete` per duplicate (`:162`), `delete` premature SPEC rows (`:176`), `save` stale→APPROVED (`:221`), `save` reassignment (`:230`). Each is its own statement and commit, and fires the trigger if present.
   - `AC:237` **`tenderRepository.findAll()`** (Q04; every tender, every column).
   - Loop over all tenders, `AC:238-348`: skip terminal statuses (`:239`). For each tender, up to 7 conditions each call `ensurePendingApproval` → `AC:112` **seq scan of `tender_approval_requests`** (Q05), with possible inserts or updates (`:123,:133`), and possible `tenderRepository.save(t)` (`:260,:287` = SELECT + full UPDATE), `approvalRepository.save` (`:297,:313,:344`).
   - `AC:349-351` swallows any exception.
2. `AC:383-408`: 3 GROUP BY count queries for the role (Q11), with an extra 3 for Clearance when the first returns empty (`:399-403`).
3. `AC:415` `countByStatusForAdmin()`, an unfiltered GROUP BY over every approval.

**`GET /api/approvals/pending` (`AC:498-650`):**
1. `AC:515` the same reconcile as above.
2. `AC:528-577`: one of the unpaginated list queries (Q09), for example `findByStatusForMisTeam` (`TAR:79-89`) or `findByStatusForAdmin` (`TAR:127-130`). `status=ALL` uses `findAllByOrderByCreatedAtDesc` (`TAR:74`), which returns the whole approvals table.
3. `AC:586` `findAllById(tenderIds)` (Q07).
4. `AC:592-643`: in-memory SPEC filter, search, team and role filters, and DTO building. Every match goes into the response; there is no limit.

**`POST /api/approvals/{id}/review` (`AC:666-1068`, `@Transactional`):** `findById` (`:708`), an optional fallback seq scan (`:716`), tender `findById` (`:797`), then per-stage `WSS` calls that each do `findById` + 1-3 `findByTenderIdAndStage` seq scans + saves + a `TenderComment` insert (for example `WSS:398-430`, `:627-663`, `:669-706`, `:170-216` including a filesystem scan at `:208`). Then `tenderRepository.save` (`:1017` or `:1034`), approval save (`:1041`), another seq scan plus deletes (`:1044-1049`), and a comment insert (`:1060`).

**UI multiplier (VERIFIED):** mounting the Approvals Center fires `counts` + `pending` (`ApprovalsCenter.tsx:424-427`) **and** a second `pending` 400 ms later from the search-debounce effect (`:440-445`), so 3 reconciles. Every review fires `counts` + `pending` again (`:587-588`, `:621-622`). An Admin with 0 pending also auto-fires a HISTORY `pending` (`:355-359`).

There are **no external calls** (HTTP, SMTP or S3) on the GET paths (VERIFIED). The review path does filesystem I/O inside the transaction (VERIFIED, `WSS:208`).

**Leading hypothesis:** #1 combined with #2. The reconcile N+1 loop over an unindexed approvals table, run with no transaction on every `counts`/`pending` call and three times per page load, already costs tens of seconds per call. The flatness comes from the loop being sized by active-workflow tenders and approval rows (which probably did not double between the seeds) and/or from the ceiling.

## B. Search: p95 2.9 s at 50K → 8.6 s at 100K (about 3× for 2× data)

### B.1 End-to-end trace

Browser → Next.js `GET /api/tenders?search=…` (`frontend/src/app/api/tenders/route.ts:3-6`) → `proxyToBackend` (no timeout; double JSON parse at `backendProxy.ts:55-56`) → `TC:286-496`:
1. `TC:302` permission check (no DB).
2. `TC:308-314`: `findByMisExecutive(username)` for executives (`TR:60`, indexed, unpaginated), **otherwise `findAll()` (Q01): every row, every column.**
3. `TC:321-440`, a per-row Java loop: role filters; `resolveStatus` (`TC:345` → `TenderStatusResolver.java:73-110`: `split`, `compareTo`, `parseFlexibleDate`); **search as `toLowerCase().contains` on title, id, ref_no, authority and source_id** (`TC:349-357`); status, urgency, location, sector and cost filters; `BeanUtils.copyProperties` reflection copy per match (`TC:430` → `:513-523`).
4. `TC:446-462` an in-memory sort of the matches.
5. `TC:465-474`: 2 DISTINCT queries (Q03).
6. `TC:476-485` in-memory paging. The UI's background poll passes **no `limit`** (`page.tsx:957-970`), so every match is serialised.

There is **no SQL search predicate at all**: no `LIKE`, `ILIKE` or full-text. The DB cost is a full read of `tenders` whatever the search term (VERIFIED). There are no Specifications, Criteria or `Pageable` on this path (VERIFIED; the `Page<Tender>` methods at `TR:61-65` are unused by this endpoint).

### B.2 Ranked hypotheses for super-linear growth

| rank | hypothesis | evidence | label | how to confirm |
|---|---|---|---|---|
| 1 | **JVM heap or GC pressure from `findAll()` per request under concurrency.** The live set ≈ concurrent requests × N × (entity + Hibernate overhead + TEXT payload), plus lowercase copies made during the search loop. Doubling N doubles the live set. Once it approaches the 3 GB heap (`docker-compose.yml:32`), young collections promote and full or mixed GCs stall every request thread, so latency grows faster than N. The 1.5 s dashboard polls (Q01, Q13, Q17) multiply this if the load script models them. | `TC:313,349-357,430`; `-Xmx3g` | INFERRED | Run with `-Xlog:gc*:file=gc.log`, check GC pause totals and the old-gen occupancy at 50K versus 100K, then rerun 100K with `-Xmx6g`. If p95 drops a lot, this is confirmed. |
| 2 | **Queueing amplification (closed-loop saturation).** Each request's service time S is roughly linear in N (a full scan, materialisation, per-row Java work, two DISTINCT queries). At a fixed arrival rate or VU count, doubling S pushes utilisation toward 1, and response time = wait + S grows like S/(1-ρ). That alone turns 2× work into about 3× latency. | `TC:286-496` (all linear work per request) | INFERRED | Measure single-user (1 VU) latency at 50K and at 100K. If that ratio is about 2× while p95 under load is 3×, the difference is queueing. Check throughput (RPS) in both runs. |
| 3 | **The Postgres working set falls out of cache at 100K.** `tenders` with TEXT/TOAST (AI summaries, `downloaded_docs` JSON) might fit in `shared_buffers` or the OS cache at 50K but not at 100K, so each full scan becomes partly disk-bound and concurrent scans compete for I/O. Detoasting large TEXT for every row adds CPU. | `Tender.java:71-75,173-177,266`; Q01 reads every column | INFERRED | `SELECT pg_size_pretty(pg_table_size('tenders')), pg_size_pretty(pg_total_relation_size('tenders'));` against `SHOW shared_buffers` and instance RAM; `EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM tenders;` at both sizes, comparing `shared hit` with `read`. |
| 4 | **Response size.** If the search term in the load script is broad (or empty, or it is the poll path with no `limit`), the number of matches grows with N, and so do serialisation by Jackson, then by Node (`backendProxy.ts:55-56`), plus network. | `TC:476-495`, `page.tsx:957-970` | INFERRED | Record response bytes per request at 50K and 100K, and the search terms the script uses. |
| 5 | **Contention from approval-endpoint traffic.** If the same test mixes in approvals calls, those (section A) also run `findAll()` on tenders (Q04) and hold the pool, so search requests wait for connections and CPU. At 100K the approvals side is heavier too. | `AC:237` | INFERRED | Run a search-only scenario at 100K and compare. |
| 6 | **The DISTINCT location/sector queries** (Q03) with a sort on TEXT: n log n but small. **The in-memory sort** (`TC:446`): n log n on matches only. Both are minor. | `TR:74-90`, `TC:446-462` | INFERRED (minor) | `EXPLAIN (ANALYZE, BUFFERS) SELECT DISTINCT location FROM tenders WHERE location IS NOT NULL AND location <> '' ORDER BY location;` |

**Leading hypothesis:** each search does linear full-table work (#1 through #3), and that becomes super-linear through GC pressure on a 3 GB heap and queueing near saturation. Search terms never reach SQL, so no index can help until the filter, sort and paging move into the query.
